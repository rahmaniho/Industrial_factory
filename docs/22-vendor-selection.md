# ۲۲. انتخاب تأمین‌کننده و قرارداد (Vendor Selection & Contracting)

> انتخاب نرم‌افزار در این پروژه، یک تصمیمِ **۵ تا ۱۰ ساله** است. این سند چارچوبِ بی‌طرفانهٔ
> ارزیابی را فراهم می‌کند تا انتخاب بر اساس «رابطه» یا «دموی زیبا» انجام نشود.

## ۲۲-۱. مدل ارزیابی (وزن‌ها)

| # | معیار | وزن | آنچه واقعاً می‌سنجیم |
|---|---|---|---|
| ۱ | **تناسب عملکردی با سناریوهای ما** | ۲۰٪ | فقط با سناریوهای واقعیِ این پروژه (F1–F7، گیت‌های سخت) |
| ۲ | **یکپارچه‌سازی و باز بودن** | ۲۰٪ | API مستند، webhook/رویداد، خروجِ کامل داده، بدون قفل‌شدنِ داده |
| ۳ | **امنیت و انطباق OT** | ۱۰٪ | پشتیبانی از IEC 62443، MFA، RBAC/ABAC، Audit Trail غیرقابل‌تغییر، گواهی‌ها |
| ۴ | **بومی‌سازی (فارسی/RTL/شمسی)** | ۱۰٪ | RTL واقعی (نه ترجمهٔ رابط)، تقویم شمسی، واحدها/ارزها، چاپِ اسناد محلی |
| ۵ | **تجربهٔ صنعت مشابه و منابع محلی** | ۱۰٪ | پروژه‌های اجراشده در همان صنعت و مقیاس؛ تیمِ در دسترس در کشور |
| ۶ | **هزینهٔ کل مالکیت (TCO) در ۵ سال** | ۱۵٪ | لایسنس + پیاده‌سازی + زیرساخت + نگهداشتِ سالانه + ارتقا + نیروی انسانی |
| ۷ | **مدل پشتیبانی و SLA** | ۱۰٪ | ساعات پوشش، زمان پاسخ بر اساسseverity، مسیر تشدید، پشتیبانی محلی |
| ۸ | **نقشهٔ راه و پایداری تأمین‌کننده** | ۵٪ | سرمایه‌گذاری در محصول، فرکانس انتشار، سازگاری با استانداردهای جدید |

**نماد:** وزن‌ها باید پیش از دریافت پیشنهادها نهایی شوند (تغییر پس از آن، بی‌اعتمادی ایجاد می‌کند).

## ۲۲-۲. معیارهای حذف (Knock-out)

هر تأمین‌کننده‌ای که هر یک از این موارد را نداشته باشد، **بدون امتیازدهی حذف می‌شود**:

| # | شرط حذف | دلیل |
|---|---|---|
| K1 | نداشتن API مستند (REST یا معادل) با امکان خروج کامل داده | ADR-010 و خروج از قفل‌شدگی |
| K2 | عدم پشتیبانی از امضای الکترونیکی و Audit Trail غیرقابل‌تغییر | الزام انطباق (ADR-005) |
| K3 | عدم پشتیبانی واقعی از فارسی/RTL | الزام پذیرش کاربر |
| K4 | امکان‌ناپذیر بودنِ «قفل سیستمی» (Hard Gate) برای گیت‌های ADR-004 | هستهٔ ارزش پروژه |
| K5 | نداشتن حداقل دو پروژهٔ مرجع در صنعت مشابه با مقیاس نزدیک | ریسک اجرایی |
| K6 | عدم امکان استقرار در محل یا ابر خصوصیِ مورد تأیید (برای سامانه‌های L2/L3) | ADR-012 و الزام امنیتی |
| K7 | خودداری از تعهدِ انتقال دانش و تحویل مستندات | ریسک R16 |

## ۲۲-۳. رویکرد تدارک: یکپارچه‌ساز واحد یا بهترینِ هر حوزه؟

| مدل | مزایا | معایب | دامنهٔ پیشنهادی |
|---|---|---|---|
| **SI واحد + مجموعهٔ یکپارچه (Suite)** | مسئولیت واحد؛ یکپارچگیِ ذاتی؛ مذاکرهٔ ساده‌تر | ممکن است در برخی حوزه‌ها ضعیف باشد؛ وابستگی بالا | مناسب برای ERP + WMS + مالی |
| **بهترینِ هر حوزه (Best-of-Breed) + یکپارچه‌ساز** | بهترین قابلیت در هر حوزه؛ انعطاف | هزینه و ریسکِ یکپارچه‌سازی؛ مدیریت چند قرارداد | مناسب برای MES، LIMS، CMMS، PdM |
| **ترکیبی (پیشنهاد)** | تعادل | نیاز به یک SI قوی با قراردادِ مسئولیتِ یکپارچه‌سازی | — |

**پیشنهاد:** یک **SI با مسئولیتِ یکپارچه‌سازی** که MES/LIMS/CMMS را از تأمین‌کنندگان تخصصی می‌آورد،
و ERP/مالی را با تأمین‌کنندهٔ فعلی (در صورت توانمندی) نگه می‌دارد. شرط حیاتی:
**SI مسئولِ یکپارچه‌سازیِ سرتاسری باشد، نه فقط ماژولِ خودش.**

## ۲۲-۵. اثبات مفهوم (POC) — دو هفته، سناریو محور

دموی آماده، چیزی را ثابت نمی‌کند. POC باید **روی داده و سناریوهای خودمان** اجرا شود.

| روز | فعالیت |
|---|---|
| ۱–۲ | تحویلِ دادهٔ واقعی (نمونهٔ کالا، BOM، یک دستور کار واقعی، فهرست دارایی) |
| ۳–۵ | پیکربندیِ سناریوهای F1 و F2 روی سامانهٔ تأمین‌کننده |
| ۶–۷ | اجرای سناریوهای F3 و F4 (شامل گیت‌های سخت) |
| ۸ | تستِ یک‌پارچگی: یک رویداد از انتها به انتها با idempotency و قطعِ عمدیِ شبکه |
| ۹ | تستِ حالت آفلاین و همگام‌سازی |
| ۱۰ | ارزیابیِ امنیتی (احراز، RBAC، Audit، خروج داده) |
| ۱۱–۱۲ | بررسیِ گزارش‌سازی و شاخص‌ها؛ ارزیابیِ RTL و تقویم شمسی |
| ۱۳–۱۴ | جمع‌بندی و امتیازدهیِ نهایی توسط تیمِ ارزیابی |

**معیار پذیرش POC:** انجامِ موفقِ حداقل ۵ سناریو از ۷ سناریو، **بدون کدنویسیِ سفارشی**
(کدِ سفارشی در POC یعنی هزینه و ریسکِ پنهان در پروژه).

## ۲۲-۶. بندهای قراردادیِ غیرقابل‌مذاکره

| # | بند | چرا حیاتی است |
|---|---|---|
| C1 | **مالکیت داده و خروج کامل**: داده متعلق به کارخانه است؛ تحویلِ خروجِ کامل (schema + داده) در هر زمان و در پایان قرارداد، در قالب باز | جلوگیری از گروگان‌گیریِ داده |
| C2 | **دسترسی به API و مستندات**: API پایدار و مستند؛ هر تغییرِ شکننده با اطلاعِ ۶ ماهه | ADR-010 |
| C3 | **انتقال دانش**: مستندات، Runbook، آموزشِ تیم داخلی، و تحویلِ کد/پیکربندی؛ پرداختِ بخش نهایی منوط به تأیید انتقال دانش | ریسک R16 |
| C4 | **SLA و جریمه**: زمان پاسخ بر اساس severity، در دسترس‌بودنِ ماهانه، جریمهٔ عدم رعایت | قابلیت اتکا |
| C5 | **معیارهای پذیرشِ قراردادی**: پذیرش بر اساس سناریوهای UAT این پروژه، نه «نصب شد» | [`13-uat-checklist.md`](13-uat-checklist.md) |
| C6 | **امنیت و ممیزی**: تعهد به IEC 62443/ISO 27001، گزارش‌دهیِ حادثه ظرف ۲۴ ساعت، حقِ ممیزی | ADR-008 |
| C7 | **محرمانگی و حریم خصوصی**: پردازش داده‌های شخصی مطابق سیاست کارخانه | ریسک R20 |
| C8 | **تغییرات (Change Request)**: نرخِ از پیش توافق‌شده برای تغییرات؛ فرآیندِ کنترل تغییر | ریسک R18 |
| C9 | **تداوم و تضمین**: Escrow برای نرم‌افزارِ سفارشی؛ تعهد به پشتیبانی حداقل ۵ سال | ریسک R16/R19 |
| C10 | **تثبیت قیمت و ارز**: سازوکارِ تعدیل در صورت نوسان ارز (با سقف) | ریسک R13 |
| C11 | **منابع کلیدی**: نام بردن از افراد کلیدی و شرطِ عدم جایگزینیِ بدون تأیید | ریسک R12 |
| C12 | **تحویلِ مستنداتِ معماری**: دفترچهٔ API، مدل داده، نقشهٔ استقرار، وابستگی‌ها | نگهداشت‌پذیری |

## ۲۲-۷. اشتباهات رایج در انتخاب که این فرآیند از آن‌ها جلوگیری می‌کند

| اشتباه | پیامد | پیشگیری در این فرآیند |
|---|---|---|
| انتخاب بر اساس دموی آماده | غافلگیری در اجرا | POCِ سناریو-محور روی دادهٔ واقعی |
| نادیده گرفتن TCO (فقط قیمت لایسنس) | غافلگیری مالی در سال ۲ و ۳ | وزن ۱۵٪ برای TCO پنج‌ساله |
| پذیرش «بعداً با کد سفارشی درست می‌کنیم» | هزینه و ریسکِ پنهان | شرطِ «بدون کد سفارشی» در POC |
| نپرسیدن دربارهٔ خروج از قرارداد | قفل‌شدگی کامل | بند C1 |
| انتخابِ بدونِ نمایندهٔ کاربر | مقاومت در پذیرش | حضورِ رهبران تغییر در تیم ارزیابی |
| تمرکز روی ویژگی به‌جای یکپارچه‌سازی | جزیره‌های جدید | وزن ۲۰٪ برای یکپارچه‌سازی و باز بودن |
