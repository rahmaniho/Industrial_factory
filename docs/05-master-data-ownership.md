# ۵. فهرست داده‌های پایه و مالکیت آن‌ها (Master Data & Ownership)

> تولید‌شده از `data/master_data.csv`. 
> **قانون بنیادی پروژه:** برای هر موجودیتِ دادهٔ پایه دقیقاً یک «مالک» و یک «سیستم مرجع» وجود دارد. هر سیستم دیگر مصرف‌کننده است و حق ایجاد ندارد.

## ۵-۱. مدل حاکمیت دادهٔ پایه

```
   مالک داده (واحد)                هاب داده پایه (MDM)              مصرف‌کننده‌ها
   ┌──────────────┐  ایجاد/تغییر   ┌──────────────────┐  انتشار    ┌──────────────┐
   │ کیفیت/تولید  │──────────────► │  اعتبارسنجی      │──────────► │ ERP / MES    │
   │ نت / مالی    │  با گردش‌کار   │  نسخه‌بندی       │  API/Event │ WMS / CMMS   │
   │ HSE / HRM    │                │  ثبت در Audit    │            │ LIMS / ACS   │
   │ بازرگانی     │◄────────────── │  رد و بازگشت     │            │ BI / CRM     │
   └──────────────┘   اصلاح/توضیح  └──────────────────┘            └──────────────┘
```

| نقش | مسئولیت | ابزار تصمیم |
|---|---|---|
| **مالک داده (Data Owner)** | تعریف، کیفیت، تأیید تغییر؛ پاسخ‌گوی ممیزی | گردش‌کار تغییر در MDM |
| **متولی داده (Data Steward)** | پاک‌سازی، رفع تعارض، استانداردسازی، پایش کیفیت | قواعد اعتبارسنجی MDM |
| **دفتر مدیریت داده (DMO)** | داوری بین‌واحدی، اولویت‌بندی، گزارش کیفیت داده | داشبورد کیفیت (`K116`) |
| **مصرف‌کننده** | فقط خواندن از MDM؛ هرگونه «ایجاد محلی» ممنوع | API نسخه‌دار |

## ۵-۳. قواعد کیفیت دادهٔ پایه (Data Quality Rules)

| قاعده | شرح | اقدام خودکار در صورت نقض |
|---|---|---|
| یکتایی | کلیدهای تجاری (کد کالا، کد دارایی، کد پرسنل) تکراری نباشند | رد ثبت |
| کامل‌بودن | فیلدهای الزامیِ هر موجودیت پر باشند | قرنطینه رکورد |
| اعتبار | مقادیر در محدودهٔ مجاز و مطابق الگو (مثل کد تگ، تاریخ انقضا) | رد ثبت |
| سازگاری | ارجاع به موجودیت‌های موجود (مثل قطعه → دارایی) | رد ثبت |
| به‌هنگام‌بودن | بازنگری دوره‌ای موجودیت‌های زمان‌مند (گواهی، قیمت، MSDS) | یادآوری و انقضا |
| عدم تناقض | تعریف یکسان در همهٔ سیستم‌ها (از طریق انتشار MDM) | هشدار عدم همگام‌سازی (`A103`) |

شاخص پایش: **`K116` کیفیت دادهٔ پایه** با هدف ≥ ۹۸٪ — گزارش هفتگی به کمیتهٔ راهبری.

## ۵-۴. نکتهٔ اجرایی بحرانی

بزرگ‌ترین دلیل شکست پروژه‌های MES/ERP **کیفیت دادهٔ پایه در روز اول** است، نه فناوری.
سه اقدام غیرقابل‌مذاکره:

1. **پاک‌سازی پیش از استقرار**: هیچ داده‌ای بدون غربالگری به MDM نمی‌رود؛ هدف: ۱۰۰٪ اقلام کلاس A پیش از فاز ۳.
2. **مالکِ اسمی کافی نیست**: مالک باید «وقتِ اختصاص‌یافته» در قرارداد پروژه داشته باشد (پیشنهاد: ۲۰٪ زمان یک نفر در هر واحد در فاز ۰ و ۱).
3. **دریچهٔ ورود بسته شود**: پس از استقرار MDM، ایجاد کالا/دارایی/قطعه در ERP یا MES غیرفعال می‌شود. این سخت‌گیرانه اما حیاتی است.
